# C2.2.1 design — zero-prerequisite universal installer

Date: 2026-11-26
Repository: https://github.com/muhammadibn3bdullah/arcanum.git
Baseline inspected: `main` at `f133555`, release `v0.1.0` tag currently `dac587d`.

## Intent and why

A new user should clone Arcanum, run one platform-specific installer, authenticate their own provider, and get a working Arcanum. Today the installers assume Python ≥3.12 already exists. The required fix is distribution/bootstrap work only; the working application and five-agent/shared-room architecture must not be rewritten.

## Goals

- `install.sh` and `install.ps1` bootstrap a pinned Python runtime when the host has none, then invoke the existing `install_core.py`.
- Preserve all five Arcanum-authored skills and 83 vendored BugHunter skills (88 total), their hashes, provenance, and registry.
- Keep the existing agents, Maestro workflows, OpenCode config, Harness, Dashboard, Discord, shared rooms, DPM/Scope controls, and deterministic verification.
- Keep installation idempotent, per-user, non-destructive, and auditable.
- Publish a new release tag at the exact tested commit.

## Non-goals / anti-goals

- No application rewrite, no skill deletions, no reclassification, no silent upgrades.
- No system Python replacement, no admin rights unless strictly unavoidable, no remote script execution.
- No credentials in the repository, no fabricated provider auth or desktop integration claims.
- No old-fork dependency, no deletion of `Hackbot-agents` or migration backups.

## Constraints

- Supported: Linux x86_64/ARM64, macOS x64/ARM64, Windows x64. Windows ARM64 remains unsupported because RunMaestro/Maestro v1.1.1-RC has no matching artifact.
- Maestro must be `RunMaestro/Maestro` v1.1.1-RC, never `mobile.dev`.
- Python project runtime requires ≥3.12; pinned manifest must be extended with bootstrap artifacts.
- CI runs on ubuntu/macOS/windows but cannot prove desktop Maestro integration; that distinction must remain explicit.

## Approaches considered

1. **OS package managers + python.org installers with Linux source build.** More literally “official”, but requires compilers/root on Linux and produces inconsistent artefacts. Rejected: poor reproducibility and worse zero-prerequisite UX.
2. **Standalone CPython bundle (chosen).** A pinned `astral-sh/python-build-standalone` release supplies checksum-verified archives for Linux/macOS/Windows. A small shell/PowerShell bootstrap detects the host, downloads the exact asset, verifies SHA-256, extracts under `ARCANUM_HOME`, verifies `python --version`, then runs the existing Python installer engine with that interpreter. It is not python.org-branded, but it is a standard CPython distribution with published checksums and one reproducible mechanism across platforms. The user chose this approach.
3. **Bootstrap via a pinned `uv` binary then `uv python install`.** Short implementation but adds another tool and still depends on the same standalone Python artefacts. Rejected as unnecessary indirection.

## Design

### Bootstrap layer

- `installers/bootstrap/common.sh` (sourced by `install.sh`) and `installers/bootstrap/bootstrap.ps1` (called by `install.ps1`).
- These scripts contain no application logic. They perform: OS/arch detection, disk/permission checks, existing-interpreter probe, manifest read (via a minimal parser or a copied JSON fragment where no Python exists), checksum download and verification, extraction into `<ARCANUM_HOME>/runtime/python`, version check, and exec of the Python engine.
- Existing valid Python ≥3.12 is used first; otherwise bootstrap installs pinned standalone CPython per-user.
- Downloads use HTTPS and published SHA-256; no `curl | sh`, no unverified remote execution.
- If a platform has no pinned artefact, print `UNSUPPORTED` with manual fallback and exit non-zero.

### Installer engine changes

- `step_python` accepts an explicit bootstrap interpreter path and records it in the install state/report.
- Manifest gains `python.bootstrap` with exact asset URLs, SHA-256, versions, and platform keys.
- Stage order remains: platform → bootstrap Python → deps → Bun/OpenCode/Maestro → skills/registry/agents/playbooks/shared rooms → DB/Dashboard/Discord/report.
- Five-skill and 88-skill validation becomes an explicit install stage with per-file hash checks and OpenCode discovery assertions.

### Safety and upgrade

- Existing interpreter/config/database untouched; all Arcanum runtime data under `ARCANUM_HOME`.
- Re-run is idempotent; changed files are timestamped backups.
- Locally modified skills are detected by hash and preserved with a conflict report rather than overwritten.
- Provider/Discord authentication reported as `Needs authentication` when absent.

### Release

- Implement, run tests and clean-clone installer checks, record tested SHA.
- Move `main` to that SHA; tag and publish `v0.1.1` at that exact SHA with checksums.
- Do not rewrite `v0.1.0`; document the mismatch.

## Resolved builder-review questions

1. **Host tooling baseline:** the shell bootstrap may assume standard OS utilities (`curl` or `wget`, `tar`/`unzip`, `sha256sum`/`shasum`); Windows may assume PowerShell 5.1 builtins (`Invoke-WebRequest`, `Expand-Archive`, `Get-FileHash`). If those are absent, the installer reports `UNSUPPORTED` with a manual fallback. This is an OS-level prerequisite, not a Python/application prerequisite, and must be stated in the platform matrix. (Builder call.)
2. **Release operations:** after all mandatory tests pass on the exact tested commit, push `main`, create/push `v0.1.1`, and publish the GitHub Release. This is explicitly requested in the phase spec. (Already decided by requester.)
3. **Release checksums:** this repository ships a source installer, not compiled platform binaries. Publish a `checksums.txt` manifest of tracked source files plus the pinned upstream artifact SHA-256s from `config/dependencies.json`; do not invent platform packages. (Builder call.)
4. **`--check` behavior:** it stays strictly write-free. Without suitable Python it reports `Unsupported`/`Needs manual action` for Python and downstream stages; it never downloads or extracts a runtime. (Already answered by the current documented `--check` contract.)
5. **Shared rooms stage:** shared-room setup is verification-only. Installer never seeds rooms; the runtime creates one canonical room lazily after a target is authorized. Add report/test rows, not a database-write stage. (Already answered by non-destructive DB policy and C2.1.4 architecture.)
6. **PowerShell version:** Windows PowerShell 5.1 is in scope because the documented entry point calls `powershell -File ...`. `bootstrap.ps1` must be 5.1-compatible; PowerShell 7 is optional, not required. (Already decided by requester.)

## Builder latitude

- Exact standalone Python release version and asset names are to be pinned from live release metadata at implementation time and recorded in `config/dependencies.json`.
- Shell/JSON parsing details without Python are builder choices as long as no unverified remote code is executed.
- Test harness layout under `tests/installation/` is a builder choice consistent with existing tests.

## Acceptance evidence required

- Fresh-clone Linux install with no suitable preinstalled Python (container or sandbox) completes bootstrap and mandatory stages.
- macOS and Windows installer syntax/checks and any CI-installable stages pass; desktop-only stages explicitly reported as not verifiable in CI.
- 88-skill registry and five custom skill hashes verified after install.
- Shared-room and real controlled specialist execution verified from installed runtime where provider quota allows.
- Release tag resolves to tested commit.
